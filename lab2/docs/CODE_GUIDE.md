## 1. Кадр

Порядок тот же, что в ЛР №1: `initialize` → цикл `update` / `prepare` / `render` / `submitAndPresent` → `shutdown`.

- [initialize](../source/application.cpp#L667): `createGeometry` (три сетки) → `createDescriptors` (буферы,
  layouts, пул, наборы) → `createPipelines` (два layout и три конвейера).
- [update](../source/application.cpp#L702): только интерфейс ImGui и состояние сцены на CPU.
- [render](../source/application.cpp#L740): `uploadUniforms` записывает все буферы, потом команды:
  цилиндры освещённым конвейером, затем (если включено) маркеры.

## 2. Маршрут чтения

### Шаг 1. Нормали — [geometry.cpp](../source/geometry.cpp#L14)
- Строка 25: четыре «кольца» вершин: обод верхней крышки, обод нижней, верх бока, низ бока. `ring(кольцо, i)`
  даёт индекс вершины: `2 + кольцо · 50 + i`.
- Строки 32–46: у вершин крышек нормаль `up = (0, −1, 0)` или `−up`, у вершин бока — `radial = (cos a, 0, sin a)`.
  Позиции у кольца крышки и кольца бока одинаковые, нормали разные.
- Треугольники те же, что в ЛР №1, только крышки берут вершины своих колец, а бок — своих.
- [makeCube](../source/geometry.cpp#L67): 8 углов, номер угла в двоичном виде = (z, y, x): бит 0 → x и т.д.
  Обход граней такой же, как у цилиндра (видимые снаружи — по часовой стрелке на экране).
- [makeConeLines](../source/geometry.cpp#L88): вершина + 16 точек окружности; индексы парами — отрезки.

Вопросы: почему 202 вершины, а не 102? Что будет с освещением, если у вершин обода оставить одну нормаль?

### Шаг 2. Камера — [scene.cpp](../source/scene.cpp#L24)
- `rotationMatrix(yaw, pitch)` = `Ry(yaw) · Rx(−pitch)` (строка 24). Общая для камеры, направленного света и прожектора.
- `forwardDirection` (30): куда повёрнута ось +z — направление взгляда камеры или света.
- `cameraAround` (34): камера на расстоянии от начала координат, смотрящая на него; используется для камеры
  по умолчанию и для `LAB1_CAMERA_PITCH`.
- [viewMatrix](../source/scene.cpp#L176): `transpose(R) · translate(−position)` — обратная к `T · R` по правилам
  со слайда 10. Юнит-тест сравнивает её с `glm::inverse(T · R)`.

Вопросы: почему обратная к повороту — транспонированная? Почему порядок множителей в обратной меняется?
Куда сдвинется картинка, если камеру сдвинуть вправо?

### Шаг 3. Источники и материал на CPU — [scene.hpp](../source/scene.hpp#L78)
- `Object` (78): к трансформации добавлены `albedo`, `specular`, `shininess` — материал своего объекта.
- `AmbientLight`, `DirectionalLight`, `PointLight`, `SpotLight` (99–125): значения по умолчанию — начальная сцена.
  Цвета sRGB, как в палитре интерфейса.
- `Lights` (131): рассеянный, направленный и два массива `std::vector`; `max_point_lights = max_spot_lights = 16` —
  размер storage-буферов.
- Перевод в данные шейдера ([scene.cpp:117](../source/scene.cpp#L117)–161):
  - `radiance` (18): `sRGB → линейный × интенсивность`;
  - `sceneUniforms` (127): направление света из yaw/pitch, число источников не больше размера буфера;
  - `spotLightUniforms` (146): косинусы углов, внешний угол не меньше внутреннего;
  - `spotConeMatrix` (157): матрица конуса маркера, `r = L · tan(внешний угол)`.

### Шаг 4. Раскладка памяти — [uniforms.hpp](../source/uniforms.hpp)
- Структуры C++ один в один повторяют блоки шейдеров. Каждый `glm::vec3` в паре с 4-байтовым полем
  (`point_light_count`, `cos_inner`, …) или `padding` — так выглядит выравнивание `vec3` на 16 байт в std140/std430.
- `static_assert` внизу фиксируют смещения. Те же числа тест `uniform_layout` читает из SPIR-V.

Вопрос: что увидим, если убрать `padding0` в `PointLight`? (C++ будет класть `color` на смещение 12, шейдер читать
с 16: цвет «съедет», а шаг массива станет 24 вместо 32 — все источники после первого перепутаются.)

### Шаг 5. Шейдеры — [object.vert](../shaders/object.vert), [object.frag](../shaders/object.frag)
- [uniforms.glsl](../shaders/uniforms.glsl): `SceneUniforms` (set 0, binding 0) и `ObjectUniforms` (set 1,
  binding 0), подключается в оба шейдера через `#include`, чтобы не держать две копии.
- `object.vert` (15): переводит позицию в мир и на экран; нормаль — `transpose(inverse(mat3(model)))`;
  альбедо умножает на цвет вершины, если включено.
- `object.frag`:
  - строки 27–33: storage-буферы с массивами **без размера**;
  - `blinnPhong` (37): формула для одного источника, ноль при `n · l ≤ 0`;
  - `main` (49): рассеянный + направленный (55) + цикл по точечным (57) + цикл по прожекторам (63);
    мягкий край — строка 72.

Вопросы: зачем `normalize(in_normal)` во фрагментном шейдере, если нормали вершин единичные? (После интерполяции
между двумя единичными векторами длина меньше 1.) Почему для направленного света `l = −direction`?

### Шаг 6. Дескрипторы и буферы — [createDescriptors](../source/application.cpp#L162)
- Буферы: `scene_uniform_buffer`, `point_light_buffer` и `spot_light_buffer` (`VK_BUFFER_USAGE_STORAGE_BUFFER_BIT`,
  размер `16 · sizeof(...)`), 8 буферов объектов.
- Layout set 0 — три binding: UBO для вершинного и фрагментного шейдера, два SSBO для фрагментного. Layout set 1 — UBO.
- Пул: `UNIFORM_BUFFER` 1 + 8, `STORAGE_BUFFER` 2, наборов 1 + 8.
- Лямбда `write`: один `VkWriteDescriptorSet` на binding — «этот binding этого набора указывает на этот буфер».

### Шаг 7. Конвейеры — [createPipelines](../source/application.cpp#L361)
- `createPipeline` (305): общий для всех трёх конвейеров. Все сетки хранят `geometry::Vertex`; освещённому нужны три
  атрибута (позиция, нормаль, цвет), маркерам — только позиция (`attribute_count = 1`).
- Layout освещённого: `[scene_set_layout, object_set_layout]`. Layout маркеров: без наборов, один диапазон push
  constants на 80 байт.
- `GraphicsPipelineInfo::topology` (новое поле в `graphics.hpp`): `TRIANGLE_LIST` для кубов, `LINE_LIST` для конусов.

### Шаг 8. Запись буферов и отрисовка — [uploadUniforms](../source/application.cpp#L403), [render](../source/application.cpp#L740)
- `uploadUniforms`: `SceneUniforms`; каждый источник — в свой элемент storage-буфера (смещение `i · sizeof`);
  `ObjectUniforms` каждого объекта. Возвращает `P · V` для маркеров.
- `render`: bind освещённого конвейера → bind сетки цилиндра → set 0 один раз → для каждого объекта set 1 + draw.
- [drawLightMarkers](../source/application.cpp#L643): конвейер кубов, для каждого источника `vkCmdPushConstants`
  (`P·V·T·S` и линейный цвет) + draw; затем конвейер линий и конус каждого прожектора белым.
  Маркеры рисуются после цилиндров с тем же тестом глубины, поэтому цилиндр может их закрывать.

### Шаг 9. Интерфейс — [application.cpp:432](../source/application.cpp#L432)–623
- Окно **Scene** (слева): Projection (угол обзора), Camera (позиция, yaw, pitch, сброс), Lighting (показ маркеров,
  рассеянный и направленный свет), Point lights и Spot lights (список, Add, Remove, параметры), Animation.
- Окно **Objects** (справа): список объектов, Transform, Material (альбедо, цвет блика, блеск, цвет вершин).
- `lightListInterface` (497): общий шаблон списка для обоих типов источников; что показывать для одного источника,
  передаётся лямбдой. Удаление откладывается до конца цикла, чтобы не удалять элемент вектора во время обхода.
  `ImGui::PushID(i)` нужен, потому что у всех источников одинаковые подписи («Position», «Color»), а ImGui различает
  виджеты по подписи.

## 3. Как проверить, что всё работает

```bash
cmake --build --preset mingw-debug
```
```bash
./build-debug/lab1-tests.exe
```
```bash
powershell -NoProfile -File tests/integration/run.ps1
```
Юнит-тесты: 51. Интеграционные: 16; каждый запускает приложение с валидацией Vulkan и сравнивает пиксели кадра с цветом,
посчитанным по формуле Блинна–Фонга внутри теста. Что проверяет каждый — в [LAB2.md](LAB2.md#3-проверка).

## 4. Типовые вопросы на защите

| Вопрос | Ответ | Где |
|---|---|---|
| Как получается матрица вида? | обратная к матрице камеры: `Rᵀ · T(−p)` | `scene.cpp:176` |
| Откуда нормали? | генерируются в `makeCylinder`: крышки ±y, бок радиально | `geometry.cpp:32` |
| Почему нормаль умножается на `transpose(inverse(...))`? | обычная матрица модели наклоняет нормали при неравномерном масштабе | `object.vert` |
| Где модель освещения? | `blinnPhong` во фрагментном шейдере | `object.frag:37` |
| Где затухание 1/D²? | деление цвета на `distance_squared` | `object.frag:60, 74` |
| Как сделан мягкий край? | линейный переход косинуса между внешним и внутренним углом | `object.frag:72` |

| Зачем `padding` в структурах? | выравнивание `vec3` на 16 байт в std140/std430 | `uniforms.hpp` |
