## 2. Камера и матрица вида

### Матрица камеры
Камеру можно считать обычным объектом: у неё есть позиция `p` и поворот `R`. Как и для объекта, из них
собирается матрица — **матрица камеры** `C = T(p) · R`. Она переводит точки «из системы камеры в мир».

Поворот задаётся двумя углами (как в играх):
- **yaw** — поворот вокруг вертикальной оси y (> 0 — направо);
- **pitch** — наклон (> 0 — вниз, т.к. y смотрит вниз).

`R = Ry(yaw) · Rx(−pitch)`. Минус у pitch: обычный поворот вокруг x на положительный угол поднимает +z к −y (вверх),
а нам нужно, чтобы положительный pitch опускал взгляд.

Куда смотрит камера: `forward = R · (0, 0, 1)` = `(sin yaw · cos pitch, sin pitch, cos yaw · cos pitch)`.

### Матрица вида = обратная матрица камеры
Шейдеру нужен обратный перевод: «из мира в систему камеры», где камера стоит в (0, 0, 0) и смотрит вдоль +z.
Это обратная матрица: `V = C⁻¹`. Слайд 10 лекции 4 даёт готовые правила, чтобы не обращать матрицу 4×4 в общем виде:

| Матрица | Обратная | Почему |
|---|---|---|
| перенос `T(t)` | `T(−t)` | сдвинуть назад |
| поворот `R` | `Rᵀ` (транспонированная) | столбцы поворота — единичные взаимно перпендикулярные векторы, для таких `Rᵀ·R = I` |
| масштаб `S(s)` | `S(1/s)` | у камеры не нужен |
| произведение `(A·B)⁻¹` | `B⁻¹·A⁻¹` | порядок меняется |

Итого: `V = (T(p) · R)⁻¹ = R⁻¹ · T(p)⁻¹ = Rᵀ · T(−p)`.

Смысл по шагам для точки мира `x`: сначала `x − p` (точка относительно камеры), потом поворот «назад» на угол камеры.

**Пример.** Камера в `p = (0, 0, −3)`, без поворота. Точка `(1, 2, 3)` → `(1, 2, 3) − (0, 0, −3) = (1, 2, 6)`:
точка в 6 единицах перед камерой. Так и проверяет юнит-тест.

**Камера по умолчанию**: на расстоянии 3 от начала координат, смотрит на него с наклоном 25°
(`cameraAround(3, 0, 25)`): `p = −3 · forward = (0, −1.27, −2.72)` — выше и перед цилиндром.

### Вся цепочка
```
вершина объекта → M (модель) → мир → V (вид) → система камеры → P (проекция) → экран
gl_Position = P · V · M · p
```
`P · V` одинаковы для всех объектов, их произведение считается один раз на CPU и лежит в `SceneUniforms`.
`M` — у каждого объекта своя, лежит в `ObjectUniforms`. «Угол обзора» (FOV) — параметр матрицы `P` из ЛР №1.

## 3. Нормали

**Нормаль** — единичный вектор, перпендикулярный поверхности и направленный наружу. Освещение зависит
от того, под каким углом свет падает на поверхность, а угол считается от нормали.

У цилиндра:
- верхняя крышка: `(0, −1, 0)` (вверх), нижняя: `(0, 1, 0)`;
- боковая поверхность в точке с углом `a`: `(cos a, 0, sin a)` — от оси наружу.

**Почему вершин стало 202, а не 102.** Точка на ободе принадлежит и крышке, и боковой стороне, а нормали у них разные.
У вершины нормаль одна, поэтому каждая точка обода записана дважды: с нормалью крышки и с нормалью бока.
`2 центра + 50 (верхняя крышка) + 50 (нижняя) + 50 + 50 (бок) = 202`. Из-за этого край крышки резкий, а бок гладкий.

**Гладкость боковой стороны.** Бок состоит из плоских прямоугольников, но нормали вершин радиальные. GPU плавно
смешивает нормали вершин внутри треугольника (интерполяция), поэтому свет меняется плавно, и цилиндр выглядит круглым.

**Нормали после масштаба.** Если растянуть цилиндр по x в 3 раза, умножение нормали на матрицу модели тоже растянет
её по x, и она перестанет быть перпендикулярной поверхности (поверхность стала более пологой, а нормаль — наоборот,
наклонилась сильнее). Правильная матрица для нормалей — **обратная транспонированная** `(M⁻¹)ᵀ` от 3×3 части модели.
Для поворота она совпадает с самой `M`, отличается только при неравномерном масштабе. Это проверено: с `(M⁻¹)ᵀ`
цвет растянутого цилиндра совпадает с расчётом для эллипса, с обычной `M` — расходится на 95 уровней яркости из 255.

## 4. Свет и цвет

### Линейный цвет и sRGB
Свет складывается и умножается в **линейных** величинах (вдвое больше света — вдвое больше число). Экран и палитра
ImGui работают в **sRGB** — нелинейной шкале, удобной для глаза. Поэтому (как в ЛР №1): цвет из интерфейса
переводится в линейный на CPU (`glm::convertSRGBToLinear`), все расчёты в шейдере линейные, а swapchain формата
`B8G8R8A8_SRGB` сам переводит результат обратно в sRGB при записи.

### Что нужно для расчёта в точке поверхности
| Вектор | Что это |
|---|---|
| `n` | нормаль поверхности |
| `l` | направление **к** источнику света |
| `v` | направление **к** камере: `normalize(camera_position − точка)` |
| `h` | «половинный» вектор между `l` и `v`: `normalize(l + v)` |

Все векторы единичные, тогда скалярное произведение двух векторов = косинус угла между ними.

Параметры **материала** (у каждого объекта свои):
- **альбедо** `ρd` — собственный цвет поверхности (какую долю каждого цвета она рассеивает);
- **цвет блика** `ρs` — цвет отражения (у пластика белёсый, у металла — цвета металла);
- **коэффициент блеска** `α` (shininess) — чем больше, тем меньше и резче блик.

## 5. Модель Блинна–Фонга

Свет на поверхности раскладывается на три части (слайд 29 лекции):

**1. Рассеянный (ambient)** — свет «отовсюду», отражённый от окружения. Без направления, одинаков везде:
`ambient · ρd`. Нужен, чтобы неосвещённая сторона не была абсолютно чёрной.

**2. Диффузный (Ламберт)** — матовая поверхность рассеивает свет во все стороны одинаково. Яркость зависит только от
угла падения: свет, падающий наискосок, размазывается по большей площади. Множитель `n · l` = `cos θ`:
перпендикулярно — 1, по касательной — 0. Результат: `E · ρd · (n · l)`.

**3. Зеркальный (блик)** — отражение источника. Блик виден, когда `h` близок к `n`, то есть когда камера стоит
примерно там, куда отражается свет. Множитель `(n · h)^α`: при большой степени `α` значение быстро падает
при отклонении от 1, поэтому блик маленький. Результат: `E · ρs · max(n · h, 0)^α`.
(У обычного Фонга вместо `n · h` берётся угол между отражённым лучом и `v`; Блинн заменил его на `h` — проще считать.
Интеграционные тесты отличают одно от другого: подмена на Фонга их роняет.)

**Итог для одного источника** (слайд 23):
```
если n · l > 0:  C = E · (ρd · (n · l) + ρs · max(n · h, 0)^α)
иначе:           C = 0      (свет приходит со стороны «изнанки», ни рассеяния, ни блика)
```
**Итог для пикселя:** `цвет = ambient · ρd + сумма C по всем источникам`.

`E` — сколько света источника дошло до точки (радиантность): `цвет источника · интенсивность`, для точечного
и прожектора ещё делится на расстояние в квадрате.

> На слайде 18 у диффузной части написан лишний множитель `(n · l)` второй раз. На слайде 23 формула без него —
> это стандартная модель, она и реализована.

**Пример с числами** (направленный источник по умолчанию, передняя сторона цилиндра):
`l = (−0.32, −0.77, −0.56)`, `n = (0, 0, −1)` → `n · l = 0.56`. Белый материал, `E = 0.6`:
диффузная часть `0.6 · 0.56 = 0.33`, блик `0.6 · 0.21 · 0.88^32 ≈ 0.002`, рассеянный `0.05`. Итого `0.38`
(линейное) → на экране sRGB ≈ 167 из 255.

## 6. Типы источников

### Направленный (directional) — «солнце»
Бесконечно далеко, все лучи параллельны. Задаётся только направлением (куда светит) и цветом с интенсивностью.
`l = −direction` одинаков для всех точек, затухания нет.

### Точечный (point) — «лампочка»
Точка, светящая во все стороны. Для каждой точки поверхности:
```
to_light = позиция_источника − точка
D² = to_light · to_light
l = to_light / D
E = цвет · интенсивность / D²
```
**Закон обратных квадратов** (слайд 27): свет расходится по сфере, площадь которой растёт как `D²`, поэтому
на единицу площади приходится `1/D²`. Вдвое дальше — вчетверо темнее.

### Прожектор (spot) — «фонарик»
Точечный источник, который светит только внутри конуса вокруг оси `direction`. Два угла, отсчитанных от оси:
- внутри **внутреннего** угла — полный свет;
- снаружи **внешнего** — ничего;
- между ними — плавный переход (мягкий край).

```
cos θ = (−l) · direction             угол между осью и направлением на точку
cone = clamp((cos θ − cos θout) / (cos θin − cos θout), 0, 1)
E = цвет · интенсивность · cone / D²
```
Сравниваем косинусы, а не углы, чтобы не считать `acos`. Чем меньше угол, тем больше косинус, поэтому
`cos θin > cos θout`. Если углы равны, знаменатель 0: в коде он ограничен снизу `1e-4`, и получается резкий край
(так задание и формулирует: края мягкие, «если внешний угол больше внутреннего»).

**Пример.** Внутренний 8°, внешний 16°. Точка под углом 12° к оси:
`(cos 12° − cos 16°) / (cos 8° − cos 16°) = (0.9781 − 0.9613) / (0.9903 − 0.9613) = 0.58`.

## 7. Как данные попадают в шейдер

### Два набора дескрипторов (доп. задание 1)
| set | binding | Тип | Что внутри | Сколько штук |
|---|---|---|---|---|
| 0 | 0 | uniform-буфер `SceneUniforms` | `P·V`, позиция камеры, направленный и рассеянный свет, число источников | один на кадр |
| 0 | 1 | storage-буфер `PointLights` | массив точечных источников | один |
| 0 | 2 | storage-буфер `SpotLights` | массив прожекторов | один |
| 1 | 0 | uniform-буфер `ObjectUniforms` | матрица модели и материал | по одному на объект |

Set 0 привязывается один раз за кадр, set 1 — перед каждым объектом. Объекты отличаются только set 1.

### Uniform-буфер или storage-буфер
- **Uniform** (UBO): маленький, только для чтения, размер блока в шейдере фиксирован. Подходит для «одной структуры».
- **Storage** (SSBO, ключевое слово `buffer`): большой, последний член может быть **массивом без размера** `T items[]`.
  Шейдер не знает, сколько там элементов, поэтому число передаётся отдельно (`point_light_count` в `SceneUniforms`),
  и цикл идёт до него. Так задание и требует: «не задавать максимальное количество в шейдере».

На CPU буфер всё равно имеет конкретный размер: выделено место на 16 источников каждого типа, кнопка Add
отключается, когда место кончилось. Ограничение есть только в C++, не в шейдере.

### Выравнивание: почему в C++ структурах есть `padding`
Правила раскладки `std140` (uniform) и `std430` (storage) требуют, чтобы `vec3` начинался с адреса, кратного 16.
`vec3` занимает 12 байт, поэтому после него остаются 4 «лишних» байта. Если следующим идёт `float` или `uint`, он
занимает эти 4 байта, иначе там дыра. В C++ `glm::vec3` выравнивается всего на 4 — значит, дыры нужно добавить
вручную, иначе C++ и шейдер прочитают поля с разных смещений.

```
SceneUniforms:  0 view_projection (64 байта)
               64 camera_position (12) + 76 point_light_count (4)
               80 directional_light_direction + 92 spot_light_count
               96 directional_light_color + 108 padding
              112 ambient_light + 124 padding           = 128 байт
PointLight:     0 position + 12 padding, 16 color + 28 padding = 32 байта (шаг массива)
```
Смещения проверяют `static_assert` в `uniforms.hpp` и тест `uniform_layout`, который читает их из
скомпилированного шейдера (`spirv-cross --reflect`).

### Пул дескрипторов
Пул выдаёт дескрипторы по типам, поэтому в нём два размера: `UNIFORM_BUFFER`: 1 (сцена) + 8 (объекты),
`STORAGE_BUFFER`: 2. Наборов всего `1 + 8`.

## 8. Маркеры источников (доп. задание 4)

Маркер — фигура постоянного цвета, освещение к ней не применяется. Поэтому у маркеров отдельный конвейер с простыми
шейдерами `light_marker.vert/frag`: вершинный шейдер только умножает позицию на матрицу, фрагментный пишет цвет.

- **Куб** у каждого точечного источника и прожектора: ребро 0.1, цвет источника. Режим `TRIANGLE_LIST`.
- **Конус** у прожектора: белые линии от вершины к окружности основания и по окружности. Режим `LINE_LIST`
  (каждые два индекса — отрезок), поэтому для конуса отдельный конвейер — топология задаётся при создании конвейера.

Конус в `geometry::makeConeLines` единичный: вершина в (0, 0, 0), основание — окружность радиуса 1 на z = 1.
Матрица ставит его на место: `T(позиция) · R(yaw, pitch) · S(r, r, L)`, где `L` — длина, `r = L · tan(внешний угол)`.
Тогда угол между осью и боковой линией равен внешнему углу прожектора.

### Push constants
Маркеров столько же, сколько источников, и их число меняется. Заводить на каждый uniform-буфер и набор дескрипторов
неудобно. **Push constants** — маленький блок данных (до 128 байт), который кладётся прямо в командный буфер
командой `vkCmdPushConstants` перед каждой отрисовкой. Здесь 80 байт: матрица `P·V·M` (64) и цвет (16).
Для этого в layout конвейера маркеров объявлен диапазон push constants, а наборов дескрипторов там нет вообще.

## 9. Путь одного пикселя

```
CPU (render → uploadUniforms):
  SceneUniforms ← P·V, позиция камеры, направленный и рассеянный свет (линейные, × интенсивность), число источников
  PointLights[i], SpotLights[i] ← позиции, цвета × интенсивность, направление, косинусы углов
  ObjectUniforms[k] ← M, альбедо, цвет блика, блеск

Вершинный шейдер object.vert (для каждой вершины):
  мировая позиция = M · p;  gl_Position = (P·V) · мировая позиция
  нормаль = (M⁻¹)ᵀ · n;  альбедо = albedo × (цвет вершины, если включено)

Растеризация: позиция, нормаль, альбедо интерполируются по треугольнику

Фрагментный шейдер object.frag (для каждого пикселя):
  n = normalize(нормаль)  — после интерполяции длина уже не 1
  v = normalize(камера − позиция)
  цвет = ambient · альбедо + Блинн–Фонг(направленный) + Σ Блинн–Фонг(точечные) + Σ Блинн–Фонг(прожекторы)

Swapchain sRGB: линейный цвет → байты экрана
```
