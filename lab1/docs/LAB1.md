Требования: [SPEC.md](SPEC.md) · план и чекпоинты: [PLAN.md](PLAN.md) · настройка окружения: [SETUP.md](SETUP.md) ·

## Запуск
- **VS Code:** `F5` — сборка и запуск под отладчиком; задачи `test (unit)` и `test (integration)`.
- **Терминал** (из корня проекта):
  ```
  cmake --build --preset mingw-debug
  .\build-debug\vulkan-starter-app.exe
  .\build-debug\lab1-tests.exe
  powershell -NoProfile -File tests\integration\run.ps1
  ```

**Управление:** перетаскивание мышью вращает камеру, колесо приближает. Окно «Scene» (слева) —
проекция, камера, анимация; окно «Objects» (справа) — список объектов, трансформации и цвет выбранного.

## Ключевые решения (вопросы на защите)

**Почему y вниз и глубина [0, 1]?** Это канонический объём Vulkan (лекция 1). Поэтому в орто-матрице
верх объёма `t < 0`, а после перспективной проекции ближняя плоскость даёт z = 0, дальняя — z = 1.

**Почему `glm::perspectiveLH_ZO`, а не `glm::perspective`?** Обычный вариант сделан для OpenGL:
камера смотрит вдоль −z, глубина [−1, 1]. `LH_ZO` — камера смотрит вдоль +z, глубина [0, 1], и численно это
ровно матрица со слайда (юнит-тест сравнивает поэлементно). С `glm::perspective` цилиндр оказывается
за спиной камеры и экран пустой. `glm::orthoLH_ZO` принимает y как (min, max); при y вниз min y — верх экрана.

**Как получена перспективная матрица?** `Perspective = Ortho · PerspMatrix`: сначала пирамида видимости
«сжимается» в параллелепипед (x, y умножаются на n, а w = z), затем ортографическая проекция переводит
его в канонический объём. Это разложение проверяется юнит-тестом.

**Чем отличаются проекции на экране?** В ортографической размер не зависит от расстояния:
ближняя и дальняя кромки цилиндра одинаковы, верхняя кромка сбоку — прямая линия. В перспективной
дальнее меньше, кромка — дуга. Оба свойства проверяются по пикселям кадра.

**Почему обход треугольников именно такой?** В конвейере `VK_FRONT_FACE_CLOCKWISE` + `CULL_MODE_BACK`.
При y вниз грань, видимая снаружи, должна идти по часовой на экране, т.е. нормаль по правилу правой руки
`(b − a) × (c − a)` смотрит внутрь фигуры. Тест проецирует каждый треугольник камерой и проверяет это.

**Зачем два набора дескрипторов?** set 0 — данные кадра (view · projection), привязывается один раз;
set 1 — данные объекта (model, цвет), у каждого объекта свой uniform-буфер и свой `VkDescriptorSet`.
Перед каждым `vkCmdDrawIndexed` перепривязывается только set 1.

**Почему uniform-буферы пишутся в `render`, а не в `update`?** `update` вызывается до того, как
`prepare()` дождётся fence прошлого кадра, — GPU может ещё читать эти буферы. В `render` ожидание уже прошло.

**Зачем переводить цвет sRGB → linear?** Swapchain имеет формат `B8G8R8A8_SRGB` и сам кодирует линейный цвет
в sRGB при записи. ColorEdit отдаёт sRGB, поэтому без перевода 0.5 превратился бы в 0.735 (188 вместо 128).

**Почему матрица хранится по столбцам?** `glm::mat4`, как и `mat4` в GLSL std140, хранится по столбцам —
матрицу можно копировать `memcpy` без транспонирования. Совпадение смещений полей C++ и шейдера проверяет тест `uniform_layout`.

## Тесты
- **Юнит** (`tests/unit/`, doctest): соответствие матриц GLM формулам лекции, геометрия, камера, трансформации, анимация, цвета, объекты.
- **Интеграционные** (`tests/integration/run.ps1`): приложение запускается со слоем валидации
  (включая синхронизацию), кадр снимается слоем `VK_LAYER_LUNARG_screenshot`, пиксели сравниваются
  с аналитически посчитанными значениями. Тестовые переменные `LAB1_*` описаны в SPEC.md.
- Каждый тест проверен мутацией: в код вносилась типичная ошибка, и тест должен был упасть (см. PLAN.md).
