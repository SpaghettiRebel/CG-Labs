## 1. Что вообще делает программа

Программа 60–120 раз в секунду рисует **кадр** — картинку в окне. Каждый кадр:
1. Процессор (**CPU**) решает, где сейчас цилиндр, куда смотрит камера, какого он цвета.
2. CPU отправляет видеокарте (**GPU**) список команд: «нарисуй вот эти треугольники вот так».
3. GPU рисует и показывает картинку в окне.

Зачем GPU: в кадре ~1 млн пикселей, и для каждого нужно посчитать цвет. У GPU тысячи простых ядер, которые
считают пиксели параллельно. CPU делает то же по очереди — в сотни раз медленнее.

Любой 3D-объект для GPU — это набор **треугольников**. Треугольник — самая простая плоская фигура:
три точки всегда лежат в одной плоскости. Круглый цилиндр на самом деле — многогранник из 200 треугольников,
просто их много, и он выглядит гладким.

## 3. Математика

### 3.1. Координаты и векторы

Каждая точка в 3D — три числа `(x, y, z)`. В нашей лабе (как в Vulkan и в лекции):
- **x** — вправо,
- **y** — **вниз** (не вверх, как в школе!),
- **z** — вглубь экрана, от вас.

**Вектор** — тоже три числа, но это не место, а направление с длиной («сдвинуться на 2 вправо и 1 вниз»).
Точка + вектор = новая точка.

### 3.2. Матрица = преобразование

**Матрица** — таблица чисел, которая описывает, как двигать точки. Умножаешь матрицу на точку —
получаешь новую точку. Три базовых преобразования:

**Масштаб** — растянуть в `s` раз: `x' = s·x`. Матрица с `s` на диагонали.

**Поворот** на угол `a` вокруг оси z (в плоскости xy):
```
x' = x·cos(a) − y·sin(a)
y' = x·sin(a) + y·cos(a)
```
Проверка: точка (1, 0), поворот на 90° → (cos 90, sin 90) = (0, 1). Повороты вокруг x и y — то же самое
в других плоскостях.

**Перенос** — сдвинуть на `(tx, ty, tz)`: `x' = x + tx`. Проблема: умножение матрицы на вектор умеет только
умножать и складывать сами координаты, а прибавить константу не может.

### 3.3. Однородные координаты — зачем четвёртое число

Решение: добавить к точке четвёртую координату **w = 1**: `(x, y, z, 1)`. Матрица становится 4×4,
а сдвиг записывается в её последний столбец — он умножается на эту единицу и прибавляется:
```
| 1 0 0 tx |   | x |   | x + tx |
| 0 1 0 ty | · | y | = | y + ty |
| 0 0 1 tz |   | z |   | z + tz |
| 0 0 0 1  |   | 1 |   |   1    |
```
У направления **w = 0**, поэтому перенос на него не действует — и это правильно: направление «вправо»
не меняется оттого, что объект сдвинули.

### 3.4. Порядок умножения

Матрицы можно перемножить в одну. Порядок важен, и **применяется справа налево**:
`M = T · R · S` значит: сначала масштаб `S`, потом поворот `R`, потом перенос `T`.
Если поменять порядок и сначала сдвинуть, а потом повернуть, объект улетит по дуге вокруг начала координат,
а не повернётся на месте. В коде: `scene::modelMatrix` = `T · Rz · Ry · Rx · S`.

### 3.5. Путь точки до экрана: системы координат

Каждая вершина проходит цепочку, и на каждом шаге своя матрица:

| Пространство | Что это | Каким преобразованием получено |
|---|---|---|
| **локальное** | координаты вершины относительно центра самого цилиндра | — |
| **мировое** | где цилиндр стоит в сцене | **model**-матрица: позиция, поворот, масштаб объекта |
| **камеры** | как его видит камера: камера в (0, 0, 0) и смотрит вдоль +z | **view**-матрица: обратное движение камеры |
| **clip** | подготовка к проекции на плоскость | **projection**-матрица |
| **NDC** | «нормализованный» куб: x, y от −1 до 1, глубина от 0 до 1 | деление на w (делает GPU сам) |
| **экран** | пиксели окна | **viewport**: −1…1 растягивается на 0…1280 пикселей |

В шейдере вся цепочка — одна строка: `gl_Position = view_projection * model * vec4(позиция, 1)`.

### 3.6. Ортографическая проекция

Берём прямоугольную коробку, которую видит камера (от `left` до `right`, от верха до низа, от `near` до `far`),
и линейно растягиваем её в куб NDC. По одной оси это просто перевод отрезка в отрезок:
```
x' = 2·(x − left) / (right − left) − 1      left → −1, right → +1
```
Глубина: `near → 0`, `far → 1`. Размер объекта **не зависит от расстояния**: дальняя и ближняя крышки
цилиндра одинаковые. Так рисуют чертежи.

### 3.7. Перспективная проекция

В жизни дальнее выглядит меньше: размер на экране делится на расстояние, `x_экран ≈ x / z`.
Но матрица делить не умеет. Трюк: матрица кладёт глубину `z` в четвёртую координату `w`,
а GPU после шейдера сам делит всё на `w` (это **перспективное деление**).

Параметры:
- **FOV** (field of view) — угол обзора по вертикали, у нас 60°. Больше угол — шире обзор, объекты мельче.
- **aspect** — отношение ширины окна к высоте (1280/720 ≈ 1.78). Нужен, чтобы круг не стал овалом.
- **near / far** — ближняя и дальняя границы видимости (0.1 и 100). Всё вне них отсекается.

Матрица из лекции (`t = tan(FOV/2)`):
```
| 1/(aspect·t)  0     0           0          |
| 0             1/t   0           0          |
| 0             0     f/(f−n)    −f·n/(f−n)  |
| 0             0     1           0          |   ← эта строка копирует z в w
```
Пример: точка (0.5, 0, 3) → x_NDC = 0.5 / (3 · 0.577 · 1.78) ≈ 0.16 → на экране ~744-й пиксель
из 1280 (центр — 640). Та же точка на глубине 6 будет вдвое ближе к центру.

В GLM эта матрица — `glm::perspectiveLH_ZO`. Обычный `glm::perspective` сделан под OpenGL: там камера смотрит
в −z, а глубина от −1 до 1. С ним цилиндр окажется за спиной камеры.

### 3.8. Две мелочи, которые всплывают в коде

- **Хранение по столбцам.** Матрица 4×4 лежит в памяти как 16 чисел подряд — столбец за столбцом.
  Так её хранят и GLM, и шейдеры, поэтому её можно просто скопировать в видеопамять.
- **sRGB и линейный цвет.** Мониторы показывают яркость нелинейно, поэтому цвет хранят в «сжатом»
  формате **sRGB**. Считать надо в «честном» **линейном** формате. Наше окно само переводит linear → sRGB
  при выводе, поэтому цвет из палитры ImGui (он в sRGB) сначала переводим в linear —
  иначе серый 0.5 на экране станет светлее.

## 4. Как GPU рисует треугольники

### 4.1. Вершины и индексы

**Вершина** — точка треугольника плюс любые данные к ней (у нас позиция и цвет). Вершины одного объекта
лежат в **вершинном буфере** — массиве в видеопамяти.

У соседних треугольников общие вершины. Чтобы не хранить их дважды, есть **индексный буфер**: список номеров
вершин, по три на треугольник. Цилиндр: 102 вершины (50 на верхнем ободе, 50 на нижнем, 2 центра крышек)
и 600 индексов = 200 треугольников.

### 4.2. Конвейер (pipeline)

Путь от вершин до пикселей — **графический конвейер**. Часть шагов программируемая, часть фиксированная:

1. **Вершинный шейдер** (ваша программа) — запускается для каждой вершины, умножает её на матрицы → `gl_Position`.
2. **Сборка треугольников** — по три индекса.
3. **Отсечение и деление на w** — всё, что вне куба NDC, отбрасывается.
4. **Отсечение задних граней** (**culling**) — треугольники, повёрнутые к камере спиной, выбрасываются,
   их всё равно не видно. Как GPU понимает, где «спина»: по порядку обхода вершин на экране.
   Мы договорились, что лицевая сторона обходится **по часовой стрелке**.
5. **Растеризация** — треугольник превращается в набор пикселей, которые он накрывает (**фрагменты**).
   Данные вершин (цвет) плавно перемешиваются внутри треугольника — **интерполяция**.
6. **Фрагментный шейдер** (ваша программа) — запускается для каждого пикселя, возвращает его цвет.
7. **Тест глубины** — в **буфере глубины** для каждого пикселя хранится расстояние до самого близкого уже
   нарисованного. Новый пиксель рисуется, только если он ближе. Так ближний цилиндр закрывает дальний,
   в каком бы порядке их ни рисовали.

### 4.3. Шейдеры

**Шейдер** — маленькая программа, которая выполняется на GPU. Пишется на языке **GLSL** (похож на C),
компилируется `glslc` в байт-код **SPIR-V** (файлы `.spv`), который загружается в Vulkan.
У нас `shaders/object.vert` (вершинный) и `object.frag` (фрагментный).

Шейдер получает данные тремя способами:
- `in` — данные текущей вершины (позиция, цвет) или то, что передал предыдущий шейдер;
- `out` — то, что он передаёт дальше;
- `uniform` — данные, одинаковые для всех вершин при отрисовке объекта (матрицы, цвет из интерфейса).

## 5. Объекты Vulkan

В Vulkan всё — объекты, которые создаются функцией `vkCreate…` и обязательно удаляются `vkDestroy…`.
Забыли удалить — слой валидации сообщит об утечке. Ниже — в порядке, в котором они нужны.

### Настройка (делает шаблон преподавателя, `graphics_internal.cpp`)

| Объект | Что это |
|---|---|
| **Instance** | Подключение программы к Vulkan; здесь же включаются слои валидации |
| **Physical device** | Конкретная видеокарта в компьютере |
| **Device** | «Сеанс работы» с видеокартой: через него создаются все остальные объекты |
| **Queue** (очередь) | Куда отправляются команды для выполнения на GPU |
| **Swapchain** | Несколько картинок окна по очереди: одна показывается на экране, в другую в это время рисуем. Иначе было бы видно недорисованный кадр |
| **Image / ImageView** | Картинка в видеопамяти и «взгляд» на неё (как её читать). Картинки swapchain и буфер глубины — это Image |
| **Render pass** | Описание прохода рисования: в какие картинки рисуем (цвет + глубина) и что с ними делать в начале (очистить) и в конце (сохранить) |
| **Framebuffer** | Конкретный набор картинок для render pass: «вот эта картинка swapchain + вот этот буфер глубины» |
| **Fence, Semaphore** | Синхронизация. GPU работает параллельно с CPU, поэтому нужно ждать: **fence** — CPU ждёт, пока GPU закончит кадр; **semaphore** — один этап GPU ждёт другой (показ картинки ждёт окончания рисования) |

### Ваша часть (`application.cpp`, `graphics.cpp`)

| Объект | Что это |
|---|---|
| **Buffer** | Массив байтов в видеопамяти. Бывает вершинный, индексный и uniform-буфер. Память выделяет VMA. Наши буферы **отображены** (mapped): CPU пишет в них обычным `memcpy` |
| **Shader module** | Загруженный `.spv`-шейдер |
| **Pipeline** | Весь конвейер из раздела 4.2 одним объектом: какие шейдеры, формат вершин, отсечение граней, тест глубины. Настраивается один раз заранее — так GPU работает быстрее |
| **Descriptor set layout** | «Форма» набора данных для шейдера: «на месте 0 лежит uniform-буфер» |
| **Descriptor pool** | Склад, из которого выделяются наборы дескрипторов |
| **Descriptor set** | Конкретный набор: «на месте 0 лежит **вот этот** буфер». Шейдер читает uniform-данные через него |
| **Pipeline layout** | Список форм наборов, которые использует конвейер (у нас две: set 0 и set 1) |
| **Command buffer** | Список команд для GPU на кадр: «начни проход, выбери конвейер, привяжи буферы, нарисуй». Записывается на CPU, выполняется на GPU целиком |

### Дескрипторы на примере доп. задания 6

Шейдер не знает о буферах — он знает только «место» (`set = 1, binding = 0`). Набор дескрипторов говорит,
какой буфер сейчас на этом месте. Поэтому:
- **set 0** — общие данные кадра (матрица камеры + проекции), один набор, привязывается один раз за кадр;
- **set 1** — данные объекта (model-матрица, цвет), у каждого из 8 объектов свой uniform-буфер и свой набор.

Нарисовать три цилиндра = три раза «привязать set 1 объекта → нарисовать». Геометрия одна и та же,
меняются только данные в наборе.

## 6. Один кадр целиком

Цикл в `main.cpp` повторяет четыре шага:

1. **`update`** (CPU) — ImGui рисует интерфейс, ползунки меняют переменные: позиции объектов, проекцию,
   время анимации. GPU здесь ещё не участвует.
2. **`prepare`** (шаблон) — ждёт fence (GPU закончил прошлый кадр) и берёт свободную картинку из swapchain.
3. **`render`** (ваш код):
   - считает матрицы и копирует их и цвета в uniform-буферы (теперь безопасно: GPU прошлый кадр закончил);
   - записывает command buffer: начать render pass с очисткой цвета и глубины → задать viewport → выбрать
     pipeline → привязать вершинный и индексный буферы → привязать set 0 → для каждого объекта привязать
     его set 1 и нарисовать (`vkCmdDrawIndexed`) → закончить проход.
4. **`submitAndPresent`** (шаблон) — дорисовывает поверх интерфейс ImGui, отправляет команды в очередь
   и показывает картинку в окне.

Один раз до цикла — `initialize` (создать буферы, дескрипторы, pipeline), после цикла — `shutdown` (удалить).
